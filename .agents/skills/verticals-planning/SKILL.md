# Verticals Planning

Treat the board as a causal forest rooted in Life values, not a flat task list.

Read [vertical-ladder.md](references/vertical-ladder.md), [goal-contract.md](references/goal-contract.md), and [source-routing.md](references/source-routing.md) before proposing board changes. Use `$verticals-operator` before any mutation.

## Choose a mode

| Mode | Purpose | Write boundary |
| --- | --- | --- |
| Facilitate | Clarify the situation and build a working map. | Read-only. |
| Audit | Inspect goals, evidence, hierarchy, and capacity. | Read-only until the exact diff is approved. |
| Apply | Execute an already approved change. | Write only the approved set, then verify it live. |

State the mode briefly. Do not treat a planning conversation as mutation approval.

## Non-negotiable gates

Create or preserve a commitment only when a primary source proves that it exists: a direct user instruction, an explicit agreement with an owner, or a clear promise. Plans, summaries, search results, and model suggestions are discovery aids, not proof.

Keep these decisions separate:

1. **Existence:** evidence proves the commitment is real.
2. **Priority:** the parent chain proves why it matters now.
3. **Date:** explicit timing or capacity evidence proves it fits.

Every active non-value goal needs one strongest causal parent and exactly one Life value ancestor. Shared subject matter is not a causal link. Do not invent a bridge goal to repair a weak tree.

Treat the user's latest manual board edit as authoritative. Never normalize, move, rename, or reschedule it from an older draft without newer approval.

## Workflow

1. Read the relevant board slice, goal details, ancestors, and direct children.
2. Resolve the exact entity, source, and current state. Use optional connected sources only when relevant.
3. Reconstruct the chain top-down from values and bottom-up from current commitments.
4. Test every parent-child edge: “Because the parent result matters, this child result is necessary or is the chosen bet.”
5. Validate each candidate against the ladder and card contract.
6. Check capacity before assigning a date. An empty calendar is not capacity.
7. Present the exact proposed tree and mutation list: keep, rename, reparent, schedule, park, complete, delete, or create.
8. Show material body rewrites exactly as they will render.
9. Obtain explicit approval unless the user already authorized the exact mutation.
10. Apply through `$verticals-operator`, then reread and report the verified state.

## Planning conversation

Ask one primary question at a time. Agree the intended result, success test, scope boundary, and whether active redirection is welcome. Distinguish facts, hypotheses, tensions, decisions, exclusions, and experiments. Do not force every useful conclusion into a card.

When options multiply, separate exploration from commitment. A research idea becomes active work only after its boundary, expected payoff, owner, and stopping condition are chosen.

## Required output

For facilitation, return:

1. Intended result and whether it was reached.
2. Governing tension or choice.
3. Confirmed causal map across relevant verticals.
4. Facts, hypotheses, and unresolved choices.
5. Deliberate exclusions.
6. Agreed next action, success evidence, capacity basis, and review point.
7. Exact proposed board changes, or why no change is justified.

For an audit or update, return:

1. Confirmed tree.
2. Evidence-backed commitments.
3. Unsupported observations kept outside the board.
4. Missing decisions.
5. Capacity result.
6. Exact mutation list.
7. After approval: verified changes and discrepancies.
